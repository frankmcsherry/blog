# Deterministic Simulation Testing in Dataflows Timely and Differential

Differential dataflow has had [a fairly ick bug](https://github.com/TimelyDataflow/differential-dataflow/issues/801) for a while now.
We fixed it, but it wasn't evident for a long time due in part to an exotic set of needs to prompt it.
We needed to be continually updating the inputs to a doubly nested recursive dataflow, with at least three workers, under contention, re-using an arrangement in a certain way.
Something that absolutely should work, but absolutely was not anticipated by DD's smoke tests.

Finding and fixing the issue involved building out a muscle that timely hasn't much flexed: deterministic similation testing (DST).

Timely dataflow's core function is to provide the information (progress-tracked frontiers) that introduce determinism into asynchronous dataflows.
Its information allows frameworks like differential dataflow to build a deterministic experience over a highly concurrent execution substrate.
While timely dataflow is not itself deterministic, it is sufficiently determinism-adjacent that its just a hop, skip, and a jump to a determinic simulator.

This post will talk through [the bug](https://github.com/TimelyDataflow/differential-dataflow/issues/801) and [the DST harness](https://github.com/TimelyDataflow/timely-dataflow/pull/810) that came out.

## The fairly ick bug

While working on something unrelated in differential dataflow (an alternate storage substrate), some pressure tests that passed locally ended up red in CI.
This is very stressful, because differential dataflow is not meant to have flakes; its main value is providing deterministic outputs, and if that's not happening something is very wrong.
The issue reproduced, but randomly, only under contention, with multiple workers, on highly non-trivial dataflow graphs.
The problem was reliably present, but non-deterministic enough to frustrate conventional diagnosis processes.

Through total chance, a week or so prior I spent some Fable tokens putting together a deterministic simulation testing (DST) harness for timely dataflow.
This is .. surprisingly straightforward, in that timely dataflow is very nearly deterministic.
Each worker behaves deterministically, as a function of the blocks of messages they receive.
The only (known) source of non-determinism is the interleaving of worker scheduling and message delivery.

Surprisingly, though decreasingly so, when pointed at the ick bug Claude was able to find the DST harness in a branch, brought it on-line unprompted, and proved its worth by finding a deterministic reproducer.

The bug as it turns out doesn't *need* the chaos of concurrency to manifest, it just happens to be the easiest way to find it.
Claude (I almost wrote "we") localized the issue through repeated bisection, which DD's intended determinism made straightforward.
As it turns out, there is a single-worker reproduction, no non-determinism required, one the phenomena were better understood.
A self-send (a worker to itself) normally happens immediately, but in cross-scope arrangement sharing cases can be delayed by one scheduling quantum.
This was a test shadow, we were blind to these intra-worker concurrency bugs.

Although we didn't use DST to smoke out the bug, it was critical to localizing and reproducing the issue.

## Timely's execution model

Timely dataflow is system that manages a cohort of asynchronous workers that collaborate on complex dataflow graphs.
While we often draw dataflow graphs as `A -> B -> C`, the graphs in timely can be substantially more complex.
Timely dataflow supports, and users rely on, cyclic dataflow graphs, hierarchically nested graphs, at scale from thousands to millions of dataflow operators.

Timely's execution model derives from [Naiad](https://sigops.org/s/conferences/sosp/2013/papers/p439-murray.pdf), which derives from [single-program, multiple data](https://en.wikipedia.org/wiki/Single_program,_multiple_data) models.
Workers each maintain identical dataflow graphs; the data each worker receives is the only thing that varies.
Even timely's control plane, its progress and reachability subsystem, communicates using only the data plane.
In each scheduling quantum, each worker collects the messages that it has received, and then schedules the operators the messages are addressed to.

Within each scheduling quantum, timely workers are entirely deterministic.
There are no timers, no asynchronous callbacks, no external system dependencies.
Timely can even compile to WASM, a nearly deterministic platform.
The only (intended) non-determinism is the interleaving of worker scheduling and message receipt.

Although a team of timely workers is asynchronous, and highly non-deterministic, timely provides a "progress tracking" coordination mechanism to all operators.
Each asynchronous message bears a logical timestamp, and timely tracks and provides to operators a monotonic lower bound on these timestamps.
Operators receive, and can rely on, statements about the conclusion of ranges of logical times.
Frameworks like differential dataflow translate these certain statements about asynchronous messages into certain statements about asychronous computation, drawing determinism out of the non-deterministic execution.

If a message is ever delivered bearing a logical timestamp that has been marked closed, there would be a core soundness problem in the timely control plane.
If there is no such message and yet the output is non-deterministic, there is a problem in the framework above it.

## Deterministically simulating timely

All this talk of intended determinism is well and good, but when things aren't deterministic it can be hard to figure out who is to blame.

A classical challenge is that when you study a non-deterministic system, the act of studying it can change its behavior.
Bugs can vanish when you add logging, because the logging itself influences the non-determinism, and can straighten out racy execution.
With many and varied sources of non-determinism, it can be hard to isolate the ones that need to line up to show off the issues.

Deterministic simulation testing (DST) is an approach that not only draws out the determinism you need to reliably reproduce issues, but also (in its best forms) fully maps the space of non-determinism in the system under study.

In the case of timely dataflow, interleaving of communication and computation is the non-determinism to isolate.

Timely has a few communication mechanisms, but the one we'll lock in is the serializing form used between networked worker processes.
This same mechanism works between worker threads in the same process, and exists as an alternative to Rust's typed MPSC channels.
These channels have a clear boundary where workers explicitly "receive" messages as one multiplexed stream from each other worker (as opposed to each dataflow channel independently).
This communication fabric will allow us to explicitly control the delivery of messages to workers, with minimally invasive changes.

Each step in a timely simulation is an instance of either worker execution or message receipt.
We'll use an `enum` to represent these options:

```rust
pub enum Decision {
    /// Run one step of the indicated worker.
    Step(usize),
    /// Deliver up to `count` undelivered messages from `source` to `target`, in FIFO order.
    Deliver {
        /// The sending worker.
        source: usize,
        /// The receiving worker.
        target: usize,
        /// The maximum number of messages to deliver.
        count: usize,
    },
}
```

A nuance here is that `count` is an upper bound, not an exact number of messages.
This was Claude's insight, not mine: by using an upper bound all sequences of `Decision` are valid, and all fair sequences are live.
An exact number of messages to receive could result in deadlock, if each worker expects a message that some other worker has not produced.

The nuance is fascinating to me, a DST amateur, in that it draws out a distinction between exploring and reproducing.
The upper bound makes the exploration much easier, as one doesn't need to figure out a deadlock detector or other tripwires set by schedules that couldn't occur.
An exact number on the other hand would unlock parallel replay, in which each worker runs concurrently and awaits the exact numbers of messages to receive.
Both exploration and efficient reproduction seem valuable, but in light-but-not-fundamental tension with one another.
Getting both at the same time is still tbd.

## Exercising and exorcising

With the deterministic simulation harness in hand, we were able to isolate and fix the issue, and also kick the tires with some further "grinding".

The newfound determinism allowed us to perform the semantic bisection where we found that the issue was in differential dataflow, rather than timely dataflow.
We found the first moment where the output did not track the input, which was a `join` operator, which was for some reason ignoring some of its input.
Further study revealed that it was a result of two sources of truth, both "correct" but one of which had undergone logical compaction that concealed an important detail.

The fix was relatively short: don't rely on the compacted data (it shadowed the uncompacted data, which we had in hand but unwisely ignored).

Claude then proceeded to take the harness for a spin and did some further 40,000 rounds of evaluation, finding nothing.
This was a relief, but not entirely surprising: the error was not based on a complex pattern of concurrency, it manifests single-threaded, but on a (relatively) complex pattern of *computation*.
Burning cycles exploring concurrency without varying the computation leaves us with an obvious blind spot.
At the same time, "compiling and terminating Rust programs" is a space of problems that DST is not designed to explore.

## Conclusions and Directions

Deterministic simulation testing was valuable in *reproducing*, but not in *finding*, issues in timely and differential dataflow.
There is no reason it shouldn't be able to find issues, I have no doubt they exist, but I don't yet have a story for you of it doing this.

One blocker to further exercising these systems is the production of novel computations.
This is usually exhausting human effort, but .. there's perhaps a good story here based on LLMs: it's reasonable to imagine them producing computations with expected behavior and outputs, at a much higher throughput than I or others can manage.
In fact, this is what happened in this case: Claude put together some tests that varied how SCC was computed, tickling the bug

In parallel, work has started on formalizing parts of differential dataflow (the parts I find confusing) in [Lean](https://en.wikipedia.org/wiki/Lean_(proof_assistant)).
There is a different story to tell here, about how Claude was both able to produce a formally verified proof of correctness for differential dataflow's core operator logic, and then failed to correctly implement it several times in a row despite staring at the proof.
We'll do that one next.
